## When to Use This Runbook

Use the Rolling Back a Bad Deployment runbook when a code deployment, configuration change or feature flag change causes errors, wrong fees or limits, failed payments or rising alerts. If a change went out in the last two hours and symptoms started after it, roll back first and investigate later. Rollback is always preferred to a forward fix during an incident.

## Step 1: Identify the Bad Deployment

1. Check the deployment log for the affected service: `kubectl -n payments rollout history deploy/payments-api`.
2. Check the configuration repository history and the feature flag audit log for changes in the last two hours.
3. Compare the change time with the start of the symptoms on the service dashboard.

## Step 2: Roll Back a Code Deployment

1. Roll back to the previous revision: `kubectl -n payments rollout undo deploy/payments-api`.
2. Watch the rollout: `kubectl -n payments rollout status deploy/payments-api`.
3. If a database migration was part of the bad deployment, do not roll back the schema without the database reliability engineer.

## Step 3: Roll Back a Configuration Change

1. Revert the configuration commit in the config repository and let the pipeline deploy it; use the emergency path, which still runs a 5-minute canary for payments services.
2. For urgent cases, redeploy the last known good configuration version: `configctl deploy payments-api --version <previous>`.
3. For fraud-engine rule changes, restore the previous rule set from the fraud rule history.

## Step 4: Roll Back a Feature Flag

1. Set the flag to 0 percent or disabled in the feature flag console; production payments flags can only be changed by the release manager or the incident commander.
2. Confirm the flag value on a pod: `curl -s http://payments-api.payments:8080/flags/<flag_name>`.

## Step 5: Verify and Follow Up

After rolling back the bad deployment, confirm error rates and business metrics (success rates, fees, limits) are back to normal for 15 minutes. Record the rollback in the incident timeline. Check whether customers were overcharged or blocked and arrange refunds or notifications. Every rollback of a payments change is reviewed at the next CAB, as required by the Change Management Policy (POL-004).
