## Overview

The Payments Platform Architecture describes how Commercial Bank processes customer payments: own-bank transfers, interbank transfers through NationalSwitch, InstaPay instant payments, bill payments and card authorisations through the CardNet Gateway. The payments platform runs on the bank's private Kubernetes clusters in two data centres (DC-A active, DC-B warm standby) and is owned by payments engineering. All payments platform services are tier 1.

## payments-api

payments-api is the entry point of the payments platform. payments-api exposes REST endpoints to the mobile-bff, internet banking and partner channels, validates requests, applies limits and fees from configuration, calls the fraud-engine for a risk score, and routes each payment to the right rail. payments-api is stateless, runs 12 pods, and uses feature flags for routing changes. Every payment request carries an idempotency key so retries never create duplicate payments.

## payments-ledger

payments-ledger is the system of record for payment postings and available balances in the payments platform. payments-ledger writes to a PostgreSQL ledger database through PgBouncer in transaction pooling mode, with a read replica for balance queries (added in 2026). payments-ledger is the service most sensitive to peak load; salary day and month-end traffic can reach four to five times the normal peak. After every posting, payments-ledger publishes an event to the payment-events Kafka topic.

## CardNet Gateway Adapter

The cardnet-gateway-adapter connects the payments platform to the CardNet Gateway, the external card network used for point-of-sale and e-commerce card authorisations. The cardnet-gateway-adapter uses mutual TLS: a client certificate authenticates the bank to the CardNet Gateway, and the payment gateway ingress (pay-gw.commbank.example) presents a server certificate for callbacks. Since 2026-04-30 these certificates are rotated automatically; see RB-001. PIN and cryptogram operations are delegated to the HSM cluster.

## NationalSwitch Connector

The nationalswitch-connector connects the payments platform to NationalSwitch, the interbank switch used for interbank transfers, InstaPay payments to other banks and account name enquiries. The nationalswitch-connector uses separate thread pools (bulkheads) per call type and a circuit breaker on every call type, which opens when more than 50 percent of calls in a 30-second window time out. Retries use exponential backoff with jitter. Failover behaviour is described in RB-003.

## payment-events Kafka Topic

The payment-events Kafka topic carries every posted payment event from payments-ledger to downstream consumers: settlement, notifications, real-time fraud alerts, statements and the data warehouse ETL. payment-events has 48 partitions, keyed by account id to preserve order per account, with 7 days retention and archiving to object storage. Consumer lag on payment-events delays settlement; recovery is described in RB-004.

## HSM Cluster

The HSM cluster is a set of hardware security modules (hsm-01, hsm-02, hsm-03) behind a load balancer. The HSM cluster holds PIN, card and zone keys and performs PIN verification, PIN translation and card cryptogram checks for the cardnet-gateway-adapter and nationalswitch-connector. HSM firmware changes are normal changes that require CAB approval.

## Payment Flow Summary

A typical interbank transfer on the payments platform flows: mobile-bff to payments-api, fraud-engine scoring, payments-ledger reservation, nationalswitch-connector to NationalSwitch, payments-ledger posting, then an event on payment-events for settlement and notification.
