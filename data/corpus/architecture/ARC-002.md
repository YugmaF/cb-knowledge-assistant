## Overview

The Core Banking Integration architecture describes how digital and payments services at Commercial Bank connect to the core banking system, which holds customer accounts, loans, deposits and interest calculations. The core banking system is a packaged mainframe-style platform that is not called directly by channel services. All access goes through the core-banking-gateway, owned by platform engineering.

## core-banking-gateway

The core-banking-gateway is the single integration point for the core banking system. The core-banking-gateway exposes REST APIs for account lookup, balance enquiry, posting and customer details, and translates them into the core banking system's message formats. The core-banking-gateway enforces rate limits per consumer, caches static reference data for 15 minutes, and is a tier 1 service with 8 pods across two data centres.

## Online Posting Flow

In the core banking integration, payments-ledger posts completed payments to the core banking system through the core-banking-gateway in near real time. Settlement consumers read the payment-events Kafka topic and call the core-banking-gateway posting API. If the core banking system is slow, settlement consumers slow down, which can cause consumer lag on payment-events.

## Batch Window and Read-Only Mode

The core banking system runs a nightly batch from 00:30 to 04:00 for interest accrual, fees and end-of-day balances, with a longer month-end batch. During the batch window the core-banking-gateway switches to read-only mode: balance enquiries continue, and postings are queued in a durable queue and applied when the batch ends. A batch that overruns keeps the core-banking-gateway in read-only mode longer and delays statements and settlement postings.

## Extract Files for the Data Warehouse

At the end of the core banking batch, the core banking system produces extract files for accounts, loans, deposits and customers. The data warehouse ETL (dwh-etl) loads these extract files. Extract file schemas are governed by a schema contract; any new column must be announced to the data engineering team at least 10 business days in advance.

## Salary Credit Processing

Salary credits for corporate clients arrive as bulk files and are processed by the core banking integration from 05:00 on salary day, so that salary credits complete before the retail morning peak. Salary credit postings are prioritised over retail postings in the core-banking-gateway queue.

## Resilience

The core-banking-gateway uses circuit breakers on core banking calls, timeouts of 3 seconds for online calls, and idempotent posting requests with a unique posting reference. The core banking system runs active-passive across the two data centres, with a recovery time objective of 2 hours.

## Ownership

The core banking integration is owned by platform engineering, led by Hannah Lindqvist. Changes to the core-banking-gateway posting API require CAB approval and a canary under the Change Management Policy.
