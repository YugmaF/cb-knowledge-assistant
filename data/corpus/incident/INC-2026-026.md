## Summary

SEV2 incident. On 2026-08-11 an emergency configuration change set the InstaPay per-transaction limit to 1,000 instead of 1,000,000 and was pushed to all payments-api pods without a canary. InstaPay payments above 1,000 were rejected from 15:05 to 15:50.

## Impact

The InstaPay limit configuration error rejected payments for about 6,100 customers, including small businesses paying suppliers in the afternoon peak.

## Timeline

- 15:03 Emergency change to InstaPay limits deployed to all payments-api pods.
- 15:05 Alert: InstaPay rejection rate 45 percent, reason "amount exceeds limit".
- 15:20 SEV2 declared.
- 15:40 Configuration rolled back using RB-005.
- 15:50 InstaPay normal; incident resolved.

## Root Cause

The bad configuration deployment happened because the emergency change path bypassed the payments canary stage. The limit was entered in major currency units while payments-api reads the value in minor units, and no range check existed.

## Resolution

The InstaPay limit configuration was rolled back and customers were notified by push message that they could retry.

## Action Items

- Emergency changes to payments must still run a 5-minute canary (owner: Daniel Okafor).
- Add unit-aware range validation for all limit settings (owner: Nadeesha Silva).
